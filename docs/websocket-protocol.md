# StarryAgent WebSocket Protocol

This document describes the JSON protocol used when StarryAgent runs in `remotewebsocket` backend mode.

Current implementation references:
- Transport: `src/ipc/BackendWebSocketTransport.cpp`
- Shared protocol constants/helpers: `src/ipc/Protocol.h`, `src/ipc/Protocol.cpp`
- Frontend client behavior: `src/ui/BackendStore.cpp`
- Remote-mode bootstrap trigger: `src/main.cpp`

## Transport

- Protocol: WebSocket text frames carrying UTF-8 JSON objects.
- Client transport class: `BackendWebSocketTransport`.
- Each outbound message is serialized as compact JSON.
- Each inbound text frame must parse to a JSON object; otherwise the client emits `invalid backend websocket json`.

## Connection

The frontend creates a WebSocket connection to `settings.remoteBackendUrl` and optionally sends a bearer token from `settings.remoteBackendToken`.

If a token is configured, the client sends this HTTP header during the WebSocket handshake:

```http
Authorization: Bearer <token>
```

### Auto reconnect

If `settings.remoteBackendAutoReconnect` is enabled:
- the client retries automatically after disconnects
- reconnect delay is currently 1500 ms
- after a successful reconnect, the frontend requests bootstrap data again

Relevant code:
- `src/ipc/BackendWebSocketTransport.cpp:11`
- `src/ipc/BackendWebSocketTransport.cpp:90`
- `src/main.cpp:513`

## Top-level message shapes

A frame must be exactly one JSON object in one of these forms.

### Request

```json
{
  "id": "1",
  "method": "conversation.send",
  "params": {
    "text": "Hello"
  }
}
```

Fields:
- `id` — request ID generated by the client as a string
- `method` — method name
- `params` — method-specific object, omitted only conceptually; current helpers always send an object

### Response

```json
{
  "id": "1",
  "result": {
    "ok": true
  }
}
```

or

```json
{
  "id": "1",
  "error": {
    "code": "bad_request",
    "message": "Missing text"
  }
}
```

Fields:
- `id` — matches the request
- `result` — optional JSON value
- `error` — optional object

Error object shape:

```json
{
  "code": "string",
  "message": "string",
  "details": {}
}
```

`details` is optional.

### Event

```json
{
  "event": "conversation.delta",
  "data": {
    "conversationId": "conv_123",
    "rows": []
  }
}
```

Fields:
- `event` — event name
- `data` — event payload

## Request lifecycle used by the frontend

When remote mode starts and the socket connects, the frontend immediately sends:

1. `app.bootstrap`
2. `settings.get`

See `src/main.cpp:513`.

The frontend tracks pending request IDs locally and matches responses by `id` in `src/ui/BackendStore.cpp:517`.

## Event types

The frontend handles these events in `src/ui/BackendStore.cpp:404`.

### `conversations.reset`

Replaces the full frontend state.

Payload:

```json
{
  "conversations": [],
  "activeConversationId": "conv_123",
  "activeRows": [],
  "settings": {}
}
```

The frontend uses this as a bootstrap-style full snapshot.

### `conversation.activeChanged`

Payload:

```json
{
  "activeConversationId": "conv_123",
  "activeRows": []
}
```

`activeRows` is used when switching conversations or when the frontend needs a fresh active transcript.

### `conversation.rowsInserted`
### `conversation.rowsUpdated`
### `conversation.rowsRemoved`

Payload shape:

```json
{
  "conversationId": "conv_123",
  "first": 0,
  "last": 1,
  "rows": []
}
```

Notes:
- `first` and `last` are read only for inserted events and currently ignored for inactive conversations.
- For the active conversation, the frontend replaces the whole active row list from `rows` instead of applying a minimal patch.

### `conversation.toolCallComposing`
### `conversation.toolCallReady`
### `conversation.toolCallFinished`
### `conversation.delta`
### `conversation.reasoningDelta`

Payload shape:

```json
{
  "conversationId": "conv_123",
  "rows": []
}
```

For the active conversation, the frontend replaces the active rows from the supplied `rows` array.

### `conversation.streamingChanged`
### `conversation.errorChanged`
### `conversation.planChanged`
### `conversation.workdirChanged`

Payload patch shape:

```json
{
  "conversationId": "conv_123",
  "streaming": true,
  "error": "",
  "planMode": false,
  "planText": "",
  "planAwaitingApproval": false,
  "workdir": "E:/StarryAgent"
}
```

Only included fields are applied.

### `settings.changed`

Payload is a settings snapshot object. The frontend applies it directly to the local `Settings` instance.

Each item in `conversations` contains:
- `id`
- `title`
- `modeId`
- `created` — ISO 8601 with milliseconds
- `updated` — ISO 8601 with milliseconds
- `streaming` — boolean
- `error` — string
- `planMode` — boolean
- `planText` — string
- `planAwaitingApproval` — boolean
- `workdir` — string

## Conversation row schema

Rows are generated by `Protocol::conversationRow(...)` in `src/ipc/Protocol.cpp:75`.

Example:

```json
{
  "row": 0,
  "kind": "assistant",
  "text": "Hello",
  "toolCallId": "",
  "toolName": "",
  "argsText": "",
  "status": "",
  "result": "",
  "needsApproval": false,
  "imagePaths": []
}
```

Fields:
- `row` — row index
- `kind` — row kind
- `text` — main row text
- `toolCallId` — tool call ID for tool rows
- `toolName` — tool name
- `argsText` — serialized tool arguments text
- `status` — tool/status string
- `result` — tool result text
- `needsApproval` — whether the tool call awaits approval
- `imagePaths` — optional string array

The frontend maps these into its active conversation model in `src/ui/BackendStore.cpp:730`.

## Client behavior notes

### Unknown events

If the frontend receives an event it does not recognize, it currently ignores it.

### Responses

Responses are correlated by request `id`. For `settings.get` and `settings.set`, the frontend immediately applies `result` as a settings snapshot.

### Active-row update strategy

For most row-related events affecting the active conversation, the frontend replaces the full active row array from the payload rather than applying a granular diff.

### Initial bootstrap expectation

A practical remote backend should be prepared for this sequence immediately after connection:

1. WebSocket handshake
2. optional bearer auth header
3. `app.bootstrap`
4. `settings.get`

## Minimal backend compatibility checklist

A remote backend compatible with the current frontend should:

- accept text-frame JSON objects
- support bearer-token handshake auth if needed
- parse request objects with `id`, `method`, `params`
- return response objects with matching `id`
- emit event objects with `event`, `data`
- support `app.bootstrap`
- support all conversation mutation methods used by `BackendStore`
- emit row/state events in the payload shapes documented above
- return and emit settings snapshots compatible with `settingsSnapshot(...)`
